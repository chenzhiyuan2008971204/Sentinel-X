## 2. 問題列表

沒有找到 CRITICAL（重大安全漏洞）。這是「這次看過的範圍內沒找到」，不代表一定沒有。

### HIGH（嚴重影響防護能力或穩定性）

**H1　程序守衛一直佔用 CPU**
- 檔案：`src/sentinelx/protection/process_guard.py`，`ProcessGuard.check_once()`
- 原因：每 1 秒列出全部程序時，每個程序都向 Windows 查詢程式路徑，包括早就看過的程序。
- 實測：本機 254 個程序，每一輪用掉 **約 180 ms CPU**；只查程序編號只要 1.3 ms。也就是一直佔用約 **18% 的一個 CPU 核心**（一般 4 核筆電約整體 4～5%），即使沒有任何已知病毒也一樣。
- 影響：筆電耗電、風扇、電腦變慢；很可能是 Sentinel X 平常 CPU 偏高的主因。
- 修正：先只列出程序編號與建立時間，只對新出現的程序查路徑和雜湊；沒有已知病毒雜湊時整輪跳過。
- 難度：簡單
- 無害測試：同一台電腦量 60 秒 CPU，修正前後比較；啟動一個無害的自製程式，確認它的雜湊被加入「已知威脅」時仍然會被關掉（現有測試已有這個情境）。

**H2　VirusTotal 單獨就能判定「確認威脅」，而且會和 ClamAV 重複計分**
- 檔案：`src/sentinelx/core/risk.py`，`grade()`、`assess()`
- 原因：VirusTotal 有 10 家以上判毒就算「強證據」，單獨就成為「確認威脅」，接著觸發自動隔離和關閉程式。VirusTotal 的 70 家裡本來就包含 ClamAV，所以「ClamAV 中等證據＋VirusTotal 3～9 家」被當成兩個獨立引擎互相印證，其實部分是同一個判斷算兩次。
- 影響：常被很多防毒標記的「灰色軟體」（破解工具、遊戲外掛、系統工具、某些打包過的 Python 程式）可能被自動隔離。隔離可以還原，但會打斷使用者。
- 修正：VirusTotal 單獨最多判「可疑」，或提高門檻（例如 20 家以上而且佔比過半）才可單獨確認；和 ClamAV 同時命中時不算兩個獨立引擎；自動隔離要求至少一個本機引擎（ClamAV／YARA）有證據。
- 難度：簡單
- 無害測試：用假的引擎結果（不需要任何檔案）組合：只有 VirusTotal 12/70 → 應為「可疑」；ClamAV 中等＋VirusTotal 5/70 → 不應為「確認威脅」；ClamAV 強證據＋VirusTotal → 仍為「確認威脅」。

**H3　試跑室目前不能用，我未完成的修改讓試跑一定失敗**
- 檔案：`src/sentinelx/sandbox/trial.py`（`run_file()`、`humanize()`），`src/sentinelx/sandbox/guest_monitor.ps1`
- 原因：今天發現 VirtualBox 用「受限權限」在虛擬機裡執行指令，建立使用者、改電腦名稱都默默失敗。我改到一半：`run_file()` 已經會傳 `-User` 給監看腳本，但監看腳本還沒有這個參數，PowerShell 會直接拒絕執行。
- 實測：完整測試 **3 個失敗，全部在試跑室**（建置測試、日常使用者測試，以及我移除的舊偽裝功能測試）。
- 影響：介面上有「建立試跑室」和「開始試跑」按鈕，但功能做不完。這違反專案規則「沒有假功能」。
- 修正：二選一：(a) 完成修改並在真的虛擬機上跑完整流程與 4 個無害測試檔；(b) 先還原這次的修改，並在試跑室頁面清楚標示「尚未完成」、停用按鈕。
- 難度：中等
- 無害測試：只用 `tests/data/sandbox_samples` 的 4 個無害檔（安靜程式、設定開機執行、改誘餌檔名、在虛擬機內才寫出的 EICAR）。

**H4　同一個使用者的其他程式可以關掉 Sentinel X 而不被發現**
- 檔案：`src/sentinelx/app/config.py`（`ConfigStore.load/save`），資料夾 `%LOCALAPPDATA%\SentinelX`
- 原因：設定檔、資料庫、開機啟動登錄值都放在使用者可寫的位置；任何以你的身分執行的程式都可以把「即時防護」改成關閉、結束程式或刪掉開機啟動，Sentinel X 下次啟動也不會說。
- 影響：病毒可以安靜地關掉第二道防線。完全防止需要系統服務或核心驅動程式，這被你的條件第 9 條排除，所以目標是「被關掉時一定會知道」。
- 修正：(1) 設定檔每次存檔時把雜湊寫進稽核紀錄，啟動時比對，不是 Sentinel X 自己改的就警告；(2) 記錄「上次是正常結束還是被強制結束」，被強制結束就通知；(3) 開機啟動值被移除時通知（開機自動執行監看已能看到這類變化）。
- 難度：中等
- 無害測試：用文字編輯器把設定檔的 `enabled` 改成 false，再啟動 → 應該跳出警告；用工作管理員結束 Sentinel X 再開 → 應該提示上次被強制結束。

### MEDIUM（明顯需要改善）

**M1　「無法完整檢查」的新程式會被解鎖**
- 檔案：`src/sentinelx/services/protection_service.py`，`_settle_lock()`
- 原因：執行前鎖住只在「確認威脅」和「可疑」時保持上鎖；判定為「無法完整檢查」（例如 ClamAV 還沒載入完成、掃描逾時）也會解鎖。
- 影響：引擎出問題時，下載的新程式等於沒被檢查就能執行。和「引擎失敗不能被當成安全」的原則不一致。
- 修正：「無法完整檢查」保持上鎖並自動重試幾次；仍失敗就通知你，由你決定是否解鎖。
- 難度：簡單～中等
- 無害測試：用會故意出錯的假引擎，在下載資料夾放一個無害的自製 EXE → 應該仍然鎖住並出現通知。

**M2　即時防護把 VirusTotal 額度用在不重要的檔案上，還可能拖慢即時掃描**
- 檔案：`src/sentinelx/engines/virustotal.py`，`VirusTotalEngine.scan_batch()`（`MAX_WAIT_PER_BATCH_S = 20`）
- 原因：全域防護時，所有硬碟上新出現的 .exe／.dll／.pdf 都會查 VirusTotal；每分鐘只能查 4 次，一批最多會等 20 秒。
- 影響：安裝軟體或 Windows 更新時，每天 500 次的額度可能很快用完，真正重要的下載檔反而查不到；即時掃描排隊變長。
- 修正：即時防護只對下載、桌面、文件、USB（會被鎖住的地方）查 VirusTotal，而且不等待，額度不夠就直接跳過；保留一部分每日額度給手動掃描。
- 難度：簡單
- 無害測試：模擬 VirusTotal（不連網），一次放入 100 個無害 DLL 到暫存資料夾 → 不應查詢、也不應等待。

**M3　大量檔案事件時可能漏事件（未量測）**
- 檔案：`src/sentinelx/protection/realtime.py`，`FolderScanner.process_ready()`
- 原因：處理排隊檔案時，會在持有鎖的狀態下對每個檔案做開檔與讀取資訊；這段期間接收新事件的執行緒要等待。全域防護下事件量可能很大。Windows 的事件緩衝區滿了會丟掉事件，而且目前偵測不到。
- 影響：短時間大量檔案變動（解壓縮、安裝大型軟體）時，部分檔案可能沒被檢查。
- 修正：把檔案讀取移到鎖外；加入「事件遺失」的偵測與一次補掃。
- 難度：中等
- 無害測試：在暫存資料夾 10 秒內建立 20,000 個小文字檔，統計被檢查的數量是否等於建立的數量。

**M4　記憶體用量偏高（已量測，未找出原因）**
- 實測：0.15.1 開著 12 小時後，Sentinel X 約 **610 MB**，ClamAV 常駐程式約 **700 MB**（私有記憶體約 1 GB），合計約 1.3～1.6 GB。
- 影響：8 GB 電腦加上 Defender 和瀏覽器會比較緊。
- 修正：先量測是不是逐漸增加（記憶體洩漏），例如每小時記錄一次、跑 24 小時；提供「省記憶體模式」：不常駐 ClamAV，只在下載、USB 等重點位置用一次性的 clamscan。
- 難度：中等
- 注意：量測時我的測試程式正在寫入暫存檔，被你的 Sentinel X 掃描，所以當下的 CPU 讀數（Sentinel X 約一個核心的 45%）**不能代表平常狀況**，要在電腦閒置時重測。

**M5　勒索病毒警報只看「有被監看」的資料夾**
- 檔案：`src/sentinelx/services/protection_service.py`（`_file_event`）、`src/sentinelx/protection/ransomware.py`
- 原因：警報靠即時防護的檔案事件。全域防護開著時全部硬碟都有事件；關掉全域防護時，圖片、影片、音樂、OneDrive 沒有被監看，那裡的勒索行為看不到。
- 修正：不論全域防護開不開，都監看這些使用者資料夾（只收事件給勒索偵測，不一定要掃描）。
- 難度：簡單
- 備註：開機自動執行監看和勒索病毒警報是今天剛寫的，有 29 個測試（其中一個用真的 Windows 檔案事件改名 12 個無害文字檔），但**還沒在你電腦上的正式程式裡跑過**，也還沒存成版本（commit）。

**M6　試跑室的安全取決於 VirtualBox 本身**
- 檔案：`src/sentinelx/sandbox/`
- 原因：未知檔案在虛擬機裡執行，安全取決於 VirtualBox 有沒有漏洞；VirtualBox 偶爾會修正「從虛擬機逃到主機」的漏洞。Sentinel X 目前不檢查 VirtualBox 是否為最新版。已做到的：沒有網路卡、沒有共用資料夾、剪貼簿與拖放關閉、每次還原快照。
- 修正：啟動試跑前檢查 VirtualBox 版本，太舊就提醒更新並停止試跑。
- 難度：中等

## 3. 五個最嚴重的問題
1. H1 程序守衛一直吃 CPU（實測約一個核心的 18%）。
2. H2 VirusTotal 單獨就能自動隔離，並和 ClamAV 重複計分。
3. H3 試跑室不能用，而且我改到一半讓試跑一定失敗（3 個測試失敗）。
4. H4 其他程式可以安靜地關掉 Sentinel X。
5. M1 引擎出問題時，新下載的程式會被解鎖。

## 4. 最容易誤判的功能
1. **VirusTotal 判定**（H2）：灰色軟體很容易有 10 家以上判毒。
2. **YARA Forge 公開規則**：約 5,100 條，第一次量測 200 個 Windows 系統檔 0 誤判，但規則會每週更新，無法保證。目前單一 YARA 規則只會判「可疑」，不會自動隔離，這是正確的。
3. **開機自動執行監看**：沒有數位簽章的正常軟體（小工具、遊戲更新程式）新增開機項目時會跳通知。只通知不刪除，但可能讓你覺得很吵。
4. **勒索病毒黃色提醒**：20 秒內 150 個文件被修改，也可能是同步、備份或批次轉檔。

## 5. 最可能拖慢電腦的功能
1. **程序守衛**（H1，實測）。
2. **ClamAV 常駐**：約 700 MB～1 GB 記憶體（實測）。
3. **全域防護**：所有硬碟的新檔案都要掃描，加上 Windows Defender 也會掃同一個檔案（重複讀取磁碟；依規定不能修改 Defender 設定，所以無法避免，只能減少 Sentinel X 自己的工作量）。
4. **排程工作讀取**：每 5 分鐘約 3 秒（PowerShell），影響很小。

## 6. Sentinel X 自身的安全風險
- 主要風險是 H4：同一個使用者身分的程式能修改設定、結束程式。
- 隔離區：資料夾權限已收緊，隔離區被外部變更時會通知；同一個使用者理論上仍能改權限（已知限制，第 2 次審查記錄過）。
- VirusTotal 金鑰：用 Windows DPAPI 加密存放；這次審查沒有讀取它的內容。
- 外部程式呼叫：都用參數清單呼叫（沒有經過命令列解析），沒找到命令注入。
- 下載的規則：先比對大小與 SHA-256，只讀壓縮檔裡指定的一個檔案，在隔離的子程序中編譯驗證。
- 試跑室：見 M6。
- 管理員權限：平常不需要；只有使用者要求時才透過 Windows 的 UAC 視窗提升。

## 12. 在你電腦上的實際驗證（2026-11-06 下午，安裝 0.16.0 後）

- **勒索病毒警報（正式版）**：在「文件」建立一個測試資料夾，放 12 個無害文字檔，再全部改名成 `.locked`。Sentinel X 立刻在「即時防護」頁面顯示紅色警報「可能有勒索病毒正在加密你的檔案！」，並列出被改名的檔案。測試資料夾之後已刪除。
  - 當時沒有列出「寫入最多的程式」：測試檔每個不到 1 KB，而程式要寫入 1 MB 以上才會被列出（真的加密會寫入大量資料）。
  - 第二次測試（12 個 2 MB 的無害檔，共 24 MB）：警報列出了「python.exe（寫入 24 MB）」，就是測試程式本身；按「停止選取的程式」→ 確認 → 顯示「已停止 python.exe」，測試程式真的被停止。測試資料夾已刪除。
  - 觀察（N2，LOW）：清單是依「寫入量」排序，當時 Claude 應用程式自己寫入更多（約 570 MB），排在測試程式前面。真的勒索病毒通常寫入量很大會排前面，但忙碌的正常程式也可能出現在清單上，所以頁面寫著「不一定都是病毒」。日後可改成優先列出最近才啟動、或沒有數位簽章的程式。
- **防勒索誘餌檔**：已在「即時防護」打開，誘餌資料夾已放在文件、桌面、下載、圖片、影片、音樂與 OneDrive（OneDrive 的那份會同步到雲端）。
- **YARA Forge 公開規則**：已在「設定」同意並下載，使用中：版本 20261103，5,133 條規則。
- **隔離區的 22 個檔案**：全部是我跑自動測試時在暫存資料夾產生的 EICAR 測試檔（無害），被你的全域防護抓到並隔離，表示即時防護有在運作。沒有刪除，你可以自己決定要不要永久刪除。
- **新發現（N3，MEDIUM，已修正）**：程式執行時 Windows 會寫入一些資訊到程式檔，Sentinel X 把它當成「檔案變了」而把已存在的程式暫時鎖住，馬上再開一次會失敗（我在專案資料夾的 ruff.exe 遇到）。現在只鎖「新的」程式：剛建立、剛移進來（下載完成）、或 2 分鐘內建立的。已加測試。
- **試跑室改成單純版**：拿掉偽裝（筆電硬體資訊、日常使用者、生活檔案、滑鼠移動）和需要管理員權限的步驟；檔案在虛擬機的一般帳號下、`C:\SX` 資料夾裡執行。會偵測虛擬機的病毒可能裝乖，所以結果不會說「安全」。
- **新發現（N1，LOW）**：「新程式先鎖住」也涵蓋桌面。我在桌面上的專案資料夾裡打包程式時，剛產生的幾千個 .exe／.dll 在檢查完之前被鎖住，打包的啟動測試因此逾時；檢查完自動解鎖後就正常。一般使用者在桌面解壓縮免安裝軟體時也會遇到「剛解壓縮的幾十秒內打不開」。目前的做法：打包改到不受鎖定的資料夾（`build.py --dist`）。是否要讓 .dll 不上鎖、或對大量檔案改用更快的檢查，等你決定。
